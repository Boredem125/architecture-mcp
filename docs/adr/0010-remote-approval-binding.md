# ADR 0010: Remote-approval binding, nonce scope and done-record signing

Status: Accepted (24 Oct 2026). Founder approved T12b by phone; forks ruled by the founder-proxy (logged in `docs/control-plane/HANDOFF.md`, pending founder review); security b0 review at leader tier: approve with conditions C1-C9. Details: `docs/control-plane/T12B_PLAN.md`. Amendment F3 (4 Nov 2026, M3 T0b: admin-signed device-to-operator binding) is design only and was confirmed by security (L) on 5 Nov 2026 with changes (`docs/control-plane/T0B_SECURITY_REVIEW.md`); see the end of this file.

## Context

The T15 hostile review (`M2_SECURITY_SIGNOFF.md`) found that a remote approval was not bound to the request it approves (H1), that approval decisions read an unsigned `bundle.json` (H2), that `request_id` allowed path traversal (H3), and four Mediums. It also found that a verified approval used up its nonce even at 1 of 2, so dual control could never complete across two polls.

## Decision

1. **Binding (H1, C4).** The hook stamps each pending record with a fingerprint over kind, tool, exact command, exec_cwd, root, requires_dual, bundle_sequence and request_id. `apply_external` accepts an approval only if its signed payload matches that record and this device_id, project_id and org_id from verified local state. It recomputes the fingerprint before and after the claim, and the broker runs the claimed copy. The approver's user_id comes from the registry entry of the signing key, never from the payload. The key must be active and allowed in this environment. Dedup is by registry user_id. The required approval count never drops below the verified policy.
2. **Verified state only (H2, M2, C6, C7).** One accessor reads and re-verifies the signed bundle and registry against the pinned root once per decision. No decision path, the hook included, reads `bundle.json`, `registry.json`, `enrollment.json` or `last_valid_bundle` unverified; a grep test enforces this. An older signed bundle or registry prefix below the high-water mark, or below the record's stamped sequence, is refused. `apply_external` takes no caller-trusted registry, environment, policy sequence, operator or approval settings (fork F1 = A). In production the clock comes from the skew-checked state.
3. **Request ids (H3).** Strict charset and length; the path is resolved under the pending directory; symlinks and reparse points are refused; approvals are counted before any claim.
4. **Nonce scope (C1-C3).** The replay key is `(key_id, nonce)`, stored with `{request_id, payload_sha256, not_after}`. A re-send counts once only when request_id and payload hash both match; any other use is a replay, and old entries without this shape count as replays. The nonce file is saved before any claim or execution, and a failed save means nothing runs. Entries are pruned only after `not_after` plus a grace of at least the largest accepted skew. A done request can never be claimed again: `apply_external` runs only on status `pending`, and the hook always mints a fresh random request id. A valid, bound deny still wins even if its nonce entry conflicts.
5. **Done-record signing (F2 = A, M3, C8).** Remote-approved actions finish through `queue.finish`: scrub, then sign with a local `connector:<device_id>` key, then write to the location the evidence export reads. The `connector:` prefix is reserved and is never a human approver. The key is loaded before the claim; if it is missing, nothing runs. The done-record hash is written to the audit chain. This signature proves the record was not altered after it was written, not who approved it. Who approved is proved by the embedded signed approvals, which the evidence verifier re-verifies and re-binds offline against the pinned registry, recomputing `approved_by`. M3 moves the seal to the device key with tag `agg/remote-done/v1`.
6. **Operator binding (F3 = A, C5).** The server reports the operator's user_id at enroll. The connector persists it and prints it, and `--operator` must match if given. Enroll aborts, with nothing written, if the server omits it. The server's approvals route also refuses approvals from the device's enrolled operator, unless the signed bundle sets `allow_requester`.

   **Amendment (4 Nov 2026, M2 T16c, M2_DEMO 7.1 MUST).** The server refusal is now unconditional: `POST /api/v1/sync/escalations/{id}/approvals` returns 403 `operator self-approval refused` whenever the approving user is the connector's enrolled operator, whatever any `policy_bundles` row says (`ee/src/agg_cp/sync/escalations.py:1006-1012`). `allow_requester` is honoured only by the connector against its locally verified bundle (two distinct CLI approvals against the pinned registry). Reason: the server's bundle rows are one admin's unverified word in M2 (F-8, ADR 0001 Amendment A1 item 5). The sentence above is kept as the 24 Oct text; this amendment supersedes its last clause.
7. **Display rule (what you see is what you sign; T12b-2 security review, C9 item 8).** Before any human signs an approval, in the CLI signer or the web inbox, the signer shows every field covered by the binding fingerprint (kind, tool, command, exec_cwd, root, requires_dual, bundle_sequence, request_id) and every other server-supplied string it displays or signs (org_id, project_id, device_id, escalation_id). Values are shown in full, never truncated or elided. A field that contains a C0 control (U+0000-U+001F, tab and newline included), DEL (U+007F), a C1 control (U+0080-U+009F) or a Unicode bidi control (U+061C, U+200E, U+200F, U+202A-U+202E, U+2066-U+2069) is shown escaped (each such code point as visible text, either `\u{XXXX}` or `[U+XXXX]`; both forms are accepted), and approval is refused: the CLI `signer approve` exits non-zero and signs and sends nothing; the web inbox disables Approve. Deny stays allowed in both, because a deny can only stop an action. The signed payload is built from the same parsed values that were rendered, with no second fetch, so the signed value equals the displayed value, byte for byte, before escaping. Consequence: a multi-line command (for example a heredoc) cannot be approved remotely; the agent must put it in a script file, and the approver then sees the script path, not its contents (as for any script). Other invisible format characters (for example U+200B, U+FEFF) and confusable look-alike characters are shown as they are and are not refused; this is a named limit unless security extends the rule. A second named limit: a command that contains a secret the server scrubs can never be approved remotely. The value the approver sees and signs is the scrubbed one, which no longer equals the connector's upload view, so `apply_external` refuses it (fail closed). The agent has to rerun the action without the secret in the command line.
8. **Server approver-key projection (T12b-2 review, item 2).** The server's `approver_keys` table is a projection of the latest verified registry version, never an input. `store_registry_version` writes it in the same transaction as the new version, after `verify_chain` succeeds: each key in the new version is upserted on `(org_id, key_id)` with user_id, public_key, alg, kind, roles and registry_version, and `revoked_at` cleared; every row of that org whose key_id is absent from the new version gets `revoked_at` set (revocation = absent from the latest version, the same rule as the connector). No other code path writes `approver_keys`. A migration adds `UNIQUE (org_id, key_id)` after refusing to run if duplicates exist. The approvals route accepts a key only if its row is not revoked and its roles include `approver`. The connector stays authoritative: it re-verifies every approval against its own pinned registry, so the projection can only make the server refuse more, never make a connector accept. **Security ruling F5 (25 Oct 2026): a key_id that is live in two orgs is refused.** `store_registry_version` and signer link both refuse a key_id that is live (not revoked) in another org, or pending as a link in another org. RLS hides other orgs' rows, so the check runs through a SECURITY DEFINER function, as `cli_key_lookup` does. The pre-auth `cli_key_lookup`, which searches by key_id only, therefore finds at most one org. This is built in T12b-2 with the rest of section 8.

9. **Script content binding and broker shell parity (T12c).** Status: accepted (25 Oct 2026). Founder rulings: fix the script gap in M2 before T16, and fix NF-1 in M2 inside T12c. The security leader accepted D1-D5 with conditions C-c0-1 to C-c0-7, which are written in below. The PM's scope cuts are accepted.

   **Context.**
   - **The script gap (security: High).** The fingerprint binds the command string, not the file the command runs. The hook returns "pending" after at most 55 s, and the agent can then Write, Edit or symlink-swap the script before anyone approves. Local `sandbox approve` and remote `apply_external` then run bytes nobody reviewed.
   - **NF-1 (security: High on Windows).** The hook lexes the command as bash or pwsh, but `PrivilegeBroker._execute_approved` runs it with `shell=True`, which is `%ComSpec% /c`. To bash, `nf1-noop '&echo pwned> MARKER&'` is one harmless segment; cmd.exe runs a hidden second command. A variant gets around the APPROVER_CLI deny. The local path (`approval.py:199`) and the remote path (`approval.py:884`) both reach `FolderBroker().execute`. The proof is `tests/security/test_m2_t12c_nf1.py`.

   1. **Resolver.** One function, `connector/script_pin.py`, is shared by the hook and the broker. It is built on `shellwords.lex` with the shell family the hook models: pwsh if `tool_name == "PowerShell"`, else bash (the `classify.py` rule).
      - **Bound.** A command is bound only if it is exactly one static simple command: one segment, no pipe, no redirection, no assignment prefix, no indirection word, and no expansion, glob, tilde or substitution in any word. Word 0 must be an M2 interpreter, given by name or by absolute path outside root (T15b-1, 1 Nov 2026: a relative or under-root word 0 is unbound, `relative_interpreter` / `interpreter_under_root`):
        - python: base name `python`, `python3` or `python3.N`, optionally with `.exe`;
        - node;
        - bash or sh;
        - pwsh, with `-File`.

        Options must come from a fixed allowlist per family. The script is the first word that is not an option.
      - **Script file checks.** The script must exist exactly as written, relative to exec_cwd, with no extension or PATH search. It must resolve under root. Every path component from root down must be a real directory: no symlink, junction or other reparse point. The file must be regular, with a link count of 1, read from the open handle or fd (C-c0-1). It must not be under `.sandbox/`, under the key home or on a path the policy denies to the Read tool. A Windows operand with a `:` after the drive letter (an NTFS stream name) is unbound.
      - **Deferred to M3 (PM cut).** These forms are unbound in M2 (C-c0-5):
        - direct exec, on every OS: `./x.sh`, `.exe`, `.cmd`, `.bat`;
        - ruby, perl, dash and zsh;
        - the `py` launcher, `pythonw` and Windows PowerShell `powershell`.
      - **Unbound.** These are also unbound, with a reason code: `-c`, `-e` and `-p` (security rejected binding these as "none"); `-m`; preloads (`-r`, `--require`, `--import`); `-` or stdin; `source` and `.`; `bash -l` and `--rcfile`; `cmd /c`; pwsh without `-File`; a script operand in a compound, piped or redirected command; a dynamic word; an unknown option; any other interpreter family; and a missing, outside-root, protected, symlinked, junctioned, hard-linked, FIFO or directory operand.
      - **None.** A command with no script-shaped part (curl, git, kubectl) gets binding "none".
      - **Option tables.** Each family's table is tested against how that interpreter really parses its options, because a mis-tabled option could bind the wrong word.
   2. **Record and fingerprint.** The hook adds these fields to every command record:
      - `fp_v: 2`;
      - `script`: null, or `{rel (root-relative, "/" separators), sha256 (raw bytes), size, family, argv (the lexed words), script_index}`;
      - `script_unbound`: `""` or a reason code;
      - `script_preview`: null, or `{text (scrubbed UTF-8), sha256 (of text), shown, why}`.

      `_binding_fingerprint` adds `fp_v`, `script`, `script_unbound` and `script_preview.sha256` to its canonical object. It covers the preview's hash, not its text. `tool_name`, which sets the shell family, is already covered. A record without `fp_v` fails the recompute in `apply_external`, so it is never approved remotely. If such a record is approved locally, the broker check in 9.4 still refuses it when it runs a script. There is no v1 fallback.
   3. **The floor.** The floor applies when requires_dual is true, or when the workspace is enrolled (every enrolled escalation can be approved remotely).
      - **Under the floor.** The hook denies an unbound command with `SCRIPT_UNPINNABLE`. The deny message names the reason and the allowed shape: "run it as one command: `python path/x.py args`". The hook also denies a bound script whose body cannot be shown:
        - it is not UTF-8, or contains a NUL byte;
        - it is over 64 KiB;
        - it contains a C0 control other than tab, LF or CR, or a DEL, C1 or bidi control (the rule 7 sets).

        `apply_external` refuses a record whose `script_unbound` is not empty, or whose `script` is set while `script_preview.shown` is false.
      - **Outside the floor.** In a standalone workspace with a single approval, an unbound command escalates as before, and the reviewer sees "content NOT bound: <reason>".
   4. **Broker.** `FolderBroker.execute` is the only choke point, for both local and remote approvals. `shell=True` is removed from every approved-record path (C-c0-6).
      - **Shell family (NF-1).** The broker runs an approved command through the shell the hook modelled, never cmd.exe:
        - the family is pwsh if `tool_name == "PowerShell"`, else bash (the same rule as `classify.py`);
        - bash runs as `[bash, --noprofile, --norc, -c, <command>]`;
        - a PowerShell-tool record runs as `[<recorded powershell>, -NoProfile, -NonInteractive, -EncodedCommand, base64(UTF-16LE <command>)]`. The recorded binary is `pwsh` if present, else Windows PowerShell 5.1 (`%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`, which is what the PowerShell tool runs on stock Windows). Both are the pwsh family the hook models. This is the exec shell only: script binding under the floor still needs `pwsh -File` (9.1);
        - on Windows, the broker builds the bash command line itself, with the `-c` argument always double-quoted using MS C runtime escaping. The MSYS runtime therefore never globs or splits it.

        The command must reach the shell byte for byte. A corpus round-trip test proves this, with quotes, backslashes, `% ^ ! & * ?`, newlines and non-ASCII text. If a class of command cannot round-trip on an OS, the broker refuses that class there; it never guesses.
      - **Where the shells come from.** `sandbox init` already records the absolute python in `.sandbox/session.json`, which is write-protected from the agent. It now also resolves bash and pwsh once and records them as `shells: {bash, pwsh}`, each an absolute path:
        - on Windows, bash is looked up in this order, and the first candidate that passes the checks wins:
          1. the `--bash` flag;
          2. `CLAUDE_CODE_GIT_BASH_PATH` (the variable Claude Code itself uses);
          3. `%ProgramFiles%\Git\bin\bash.exe`;
          4. a path derived from the git install: `<git root>\bin\bash.exe`, where git root comes from `git --exec-path` or the `where git` location (`<git root>\cmd\git.exe`). On the demo laptop this gives `E:\Git\bin\bash.exe`;
          5. PATH lookup;
        - on POSIX, bash is the `--bash` flag, then PATH lookup;
        - the PowerShell binary is the `--pwsh` flag, then `pwsh` by PATH lookup, then the fixed System32 `powershell.exe` path above;
        - all lookups happen at init time only;
        - init refuses these candidates, at every step: a path under root, both WSL launchers (`%SystemRoot%\System32\bash.exe` and `%LOCALAPPDATA%\Microsoft\WindowsApps\bash.exe`, and any `bash.exe` under a `WindowsApps` folder), a reparse point (WindowsApps entries are app-execution aliases), and a file that is not regular. If no candidate passes, init records no bash and says why;
        - `sandbox init` prints both paths.

        At exec time there is no PATH lookup. The broker uses only the recorded path, and checks again that it is absolute, regular, not a reparse point and outside root. If the path is missing or fails a check, the request is refused: a signed `SHELL_UNAVAILABLE` done-record, and nothing runs. A workspace initialised before T12c has no `shells` field and refuses until `sandbox init` runs again. The shell binaries themselves are not hash-pinned (S-L3, C-c0-3).
      - **Re-resolve.** The broker runs the resolver again on the record's command, with the family from `tool_name`. The result must equal the record's `script`: both null, or equal objects. Otherwise it refuses.
      - **Pin and check.** If the command is bound, the broker pins the file and hashes it from the pinned handle. It compares the hash and the size with the record. It refuses (`script_changed`) on a mismatch, a missing file, a symlink, a reparse point, a link count above 1 or a file that is not regular. Every attribute is read from the open handle or fd, never from a stat taken before the open (C-c0-1). Nothing runs.
      - **Run.** It runs the lexed argv with `shell=False`, with cwd = exec_cwd and the clean environment (D2). There is no copy and no argv rewrite, so `$0`, `__file__` and `$PSScriptRoot` keep their meaning. Direct exec is deferred, so C-c0-4 (Windows argv[0] as the absolute verified path) applies only when M3 adds it.
      - **Windows pinning.** The broker opens root, each directory down to the script, and the script. It uses `FILE_FLAG_OPEN_REPARSE_POINT` for all of them, plus `FILE_FLAG_BACKUP_SEMANTICS` for the directories. The file is shared read-only; the directories are shared without delete. All handles stay open until the child exits or times out. The kernel then refuses writes, deletes and renames of the file, and renames of its folders, even by the same OS user.
      - **POSIX pinning.** The broker opens root (following links above root), then each component with `O_NOFOLLOW|O_DIRECTORY` by `dir_fd`, then the file with `O_NOFOLLOW|O_NONBLOCK`. `fstat` on that fd must show a regular file with nlink 1. The hash comes from the fd. After the child exits, the broker hashes the file again. A change sets `script_changed_during_run: true` in the done-record and raises the `script_changed` alert.
      - **Refusal.** A refusal (`SCRIPT_CHANGED` or `SHELL_UNAVAILABLE`) ends the request with a terminal done-record. It holds state `refused`, the reason code, the expected sha256, and the actual sha256 or the kind of failure. It is signed like any done-record (the local reviewer key, or `connector:<device_id>` on the remote path), chained in the audit, and raises the critical alert `script_changed` or `shell_unavailable`.
      - **Why not a copy (D1).** A private 0700 copy run under a rewritten argv is rejected:
        - (a) a copy changes `$0`, `__file__` and `$PSScriptRoot`, which breaks scripts that locate their own folder;
        - (b) a 0700 folder does not stop a writer running as the same OS user (M2 limit 4);
        - (c) the Windows share-mode lock is enforced by the kernel against the same user, and a copy is not.
   5. **What reviewers see and sign.** Rule 7 extends to scripts. CLI `sandbox approve`, `sandbox signer approve` and the web inbox show `script.rel`, sha256, size and family, then the preview body in full, with line numbers. In the body only, tab, LF and CR are rendered as layout; the hook has already refused any other control.
      - **Signed fields.** The remote approval payload adds `script_rel`, `script_sha256` and `preview_sha256` (`""` when there is no script). They are built from the displayed values. The CLI signer and the web inbox recompute the sha256 of the displayed body with WebCrypto in the browser, and refuse to sign on a mismatch.
      - **Checks.** `apply_external` requires all three fields to equal the record. The server's approvals route requires them to equal the stored escalation, and returns 400 otherwise.
      - **Server storage.** The server keeps the raw-byte metadata (`script`: rel, sha256, size) and the preview (`script_preview`: text, sha256) as separate fields. It never receives the raw bytes. An upload whose preview text is over 64 KiB is rejected (413 or 400) and never truncated (C-c0-7). The server never interprets either field.
      - **Web fallback.** If the web body view is not ready, web Approve is disabled for script escalations, with "approve in the CLI". There is never a hash-only approve.
      - **Scope line.** Every view says: "Only <rel> is bound. Files it loads are not."
   6. **Named limits (exact wording).**
      - **S-L1 Transitive code.** Only the one file named on the command line is bound. Code that it loads is not bound, and the agent can change it after approval: sourced shell files, Python imports (`conftest.py` included), Node requires, and PowerShell modules and profiles. Reviewers are told this. M3 (SENTRY_IDEAS #2).
      - **S-L2 Runners and code-from-arguments tools.** These are not content-bound: make, npm, pnpm, yarn and pytest (ADR 0009, which keeps them escalated), and tools that read code or config from their arguments (`java -jar`, `kubectl -f`, terraform, docker build). Their Makefile, `package.json` and manifests are not hashed in M2.
      - **S-L3 Interpreters, shells, PATH, config and data.** These are not bound: the interpreter binary, the recorded bash and pwsh binaries, anything found by PATH lookup (shims included), and the config and data files a script reads. The shell paths are fixed at `sandbox init`; their contents are not hashed. An absolute interpreter outside root is trusted even where the agent can write (`/tmp`, `%TEMP%`, a UNC share); the reviewer sees word 0 in the full command line (rule 7) and must judge it; M3 may pin the interpreter path to an allowlist (T15b re-review, 1 Nov 2026).
      - **S-L4 POSIX exec window.** On Linux and macOS, a process left running as the same user can swap the script between the broker's last check and the interpreter's read, or while bash reads the script line by line. The broker re-hashes the file after the run, and records `script_changed_during_run` in the signed done-record with an alert, but it cannot stop that run. Windows prevents this: the broker holds the file and its folders open with write and delete sharing denied. M3 closes it on Linux with a sealed in-memory copy. There is no macOS plan.
      - **S-L5 Command forms.** In M2, a script can be approved under the floor only as a single static command that runs python, node, bash or sh, or pwsh `-File`, with no redirection. Direct exec (`./x.sh`, `.exe`, `.cmd`, `.bat`), ruby, perl, dash, zsh, the `py` launcher and Windows PowerShell wait for M3. Under the floor they are denied, and the agent is told the allowed shape. Outside the floor they escalate, shown as "content NOT bound".
      - **S-L6 Previews.** The human signs the hash of the scrubbed body they saw (`preview_sha256`), not the hash of the raw script. The connector links that body to the raw bytes (`script_sha256`) at the hook; no human checks that link. Anything the scrubber redacted was seen by no one. A secret the scrubber misses is shown to reviewers and stored on the server. As in rule 7, invisible format characters and look-alike characters are shown, not refused.
      - **S-L7 NTFS alternate data streams.** Alternate data streams are not a swap vector. Interpreters read the file's unnamed default stream, which is the stream the hash covers, so writing a named stream does not change what runs. An operand that names a stream is unbound (9.1). Stream contents are not shown and not bound.
      - **Rejected.** General closure hashing (ADR 0009 option 3).

## Named limit (exact wording, security b0)

Operator binding (S8) is trust-on-first-use: the server reports the operator's user_id at enroll and the connector stores it in an unsigned local file. If the server is compromised at enroll time, or the operator hand-edits `enrollment.json` while the server is compromised, the operator can count as one of the two approvers of their own agent's request. Dual control then means two distinct registry humans, not two humans other than the requester. It cannot create an approval that nobody signed. Enroll prints the operator id, and `--operator` must match if it is given. Closed in M3 by an admin-signed device-to-operator binding. Severity: Low (founder ruling, 25 Oct 2026, in the terminal); fixed in M3 by the admin-signed device-to-operator binding.

## Amendment F3 (4 Nov 2026): admin-signed device-to-operator binding

M3 T0b, lead-architect. Status: Proposed, design only. Scope: `docs/control-plane/M3_PLAN.md` D5 and S10. Founder decision 4 (4 Nov 2026) and ruling T0b-1 (5 Nov 2026) make the build a MUST, last in the T9b order, movable to M4 by the founder's word, with the switch default off. "Security (L), 5 Nov 2026: ADR 0001 Amendment A9, ADR 0012 (design and spike definition only, no build), ADR 0013 including its partner-supplied certificate path (design only, T10's tests and diff review still to come) and ADR 0010 Amendment F3, as edited in this review and its addendum, are approved with S1-S4 as the cited rulings and none of the five guarded properties weakened, and plan edits P1-P9 are confirmed applied in `docs/control-plane/M3_PLAN.md`." Once built, on a device that has applied a bundle with the switch on, this replaces the trust-on-first-use text in section 6 and closes the "Named limit (exact wording, security b0)" above, within the limits below. Because the switch defaults off, that named limit stays in force word for word on every other device, and no material may call it closed without saying so.

### Context

Today the server reports `operator_user_id` at enroll and the connector stores it in `enrollment.json`, an unsigned file. `verified_state.py` reads it as it stands, and `_verify_remote_approval` uses it to exclude the requester. A compromised server at enroll, or a hand edit while the server is compromised, lets the operator count as one of the two approvers of their own agent's request. Founder ruling 25 Oct: severity Low, fixed in M3.

### Options

- **A. Admin signs before enrolment, over the code hash.** No step after enrol, but the binding names no device. A compromised server that can mint or reuse a code can attach the binding to another device.
- **B. Admin signs after enrolment, over the device's public key (chosen).** One step after enrol, and the binding cannot move to another device.
- **C. Operator listed in a registry version.** A two-admin signature for each laptop. Rejected as too heavy for a device-level fact.
- **The connector always requires a binding (rejected).** It would fail the byte-frozen M2 gate by construction, the same shape as Q3. Item 5 gets the same protection with a signed switch.

### Decision

1. **The statement.** A new tag `agg/device-binding/v1`, with `sig_v: 1` and a field set fixed in code (ADR 0007 3.2): `org_id`, `project_id`, `device_id`, `device_public_key`, `operator_user_id`, `issued_at`. `operator_user_id` is a registry user id, the same value `_verify_remote_approval` compares.
2. **Who signs.** A key with kind `cli` and the `admin` role. Browser keys are refused, even though that costs a terminal step. A compromised server serves the page's JS and can sign with the browser key of any user who loads it (ADR 0003 M2 amendment 7.2), so a browser-signed binding would not close this limit. Device and bundle-signer keys are refused. This adds a row to `may_sign` in `protocol/registry.py`. `may_sign` knows kinds, not roles, so the role check is in the connector's new code: the key's entry must carry `admin` and the key must be in the registry's admin set.
3. **Admin step.** `sandbox signer bind-device <device_id>`, under the existing approver-CLI deny (ADR 0001 A1.13). The CLI shows the org, project, device id, device key fingerprint and the operator with their `(iss, sub)` from its own verified registry, under rule 7 (section 7). An operator with no key in that registry has no verified identity there, so the CLI labels that name and subject as the server's word. The admin compares the key fingerprint with what the operator read from `sandbox enroll`, out of band, as with the root fingerprint today, and names the operator explicitly on the command line; the CLI refuses to take the server's operator as a default. The CLI signs and posts.
4. **What the connector verifies.** On fetch, and again once per decision through the one accessor of section 2: tag and field set from code; signature by a key in the latest pinned registry with kind `cli` and role `admin`; `org_id`, `project_id` and `device_id` equal to verified local state; `device_public_key` equal to this device's own key from the key home. If all pass, the operator is the binding's `operator_user_id`, and `enrollment.json` is not read for this purpose. The first verified operator is kept, and stays kept if that binding later stops verifying: a binding naming a different operator is refused (`operator_binding_conflict`), and changing operator means an admin-quorum un-enroll and a new enrolment, which gives a new device key and id (ADR 0007 M2 1.5). A verified operator that differs from `enrollment.json` raises an alert. On a managed device with no operator from either source, every remote approval is refused whatever the switch says.
5. **The switch.** A new signed field `approval.require_operator_binding` in the bundle. `false` to `true` is a tightening; `true` to `false`, including dropping the field, is a loosening and needs two `agg/policy-change/v1` approvals from distinct CLI users over the bundle hash, which covers this field, checked by the connector against its own last valid bundle. The bundle-signer signature gives no authority here (A2.2). The polarity is the reverse of `local_fallback` and `allow_requester`, so it needs its own branch in `_loosened_approval` and `_meet_approval`, never a third entry in their shared loop. The meet keeps true if either side says true. The enforced value comes from the signed bundle only, so a hand edit cannot drop it. When the enforced value is true, every remote approval on a device with no verified binding is refused (`operator_binding_pending`); denies still apply and local enforcement is unchanged. Absent means false, so M2 gate bundles behave exactly as they do now. No remote approval can precede a first bundle (`load_verified_state` gives None until one applies), so there is no window if the first bundle sets it. `sandbox signer approve-change` says so when a bundle leaves it off. Once a device has applied a bundle that sets it, a compromised server cannot drop the switch or withhold its way back to trust-on-first-use. Before that it can: see F3-L5. The switch defaults off (ruling T0b-1): the Policy page leaves it off until an admin turns it on and states F3-L5 beside the control. Only the connector's check counts.
6. **What changes in enrolment.** `sandbox enroll` keeps its flags and its abort rules (section 6). It stores the server-reported operator as today, prints it labelled `server-reported`, and adds the device key fingerprint to its output. With the switch on, the device stays `operator_binding_pending` until the binding lands; with the switch off, nothing waits. The sync cycle fetches the binding after the registry and writes it to the sync directory only after item 4 passes; a binding signed by a key this device has not pinned yet is retried, not refused for good. Each store, verify and refusal is an `admin_audit` row on the server and a chained record on the connector. Server: a route to store it (CSRF per S5 when authenticated by session), a device route to serve it, and a device-page read. The server may refuse a bad signature, but never treats a stored binding as an input to anything else (the section 8 rule).
7. **Rotation.** Item 4 uses the latest registry this device has pinned, so when the signing admin's key leaves the registry and the device pins that version, that device's binding stops verifying and the device returns to `operator_binding_pending` until another admin re-signs the same statement. This fails closed and costs availability only. A bulk re-sign command is in scope.
8. **The server refusal stays (S2).** The unconditional 403 on the enrolled operator (section 6 amendment) is unchanged. Revisit only after T4 and this amendment land, by founder decision.
9. **Label, and if deferred (decision 4, D3).** Until the build lands, the device page and any approval context label the operator **server-reported**. If F3 moves to M4 this stays through M3, the named limit above stays in force word for word at severity Low, and `M3_DONE.md` lists it as moved by the founder. After the build, the page shows "admin-signed" only when the server's check passes, and says the connector verifies for itself.

### Named limits once built (wording settled by security, 5 Nov 2026)

- **F3-L1 An admin's statement.** The binding proves an admin named this person for this device key. It does not prove who sits at the keyboard. An admin who is the real operator can name someone else and then count as an approver. The defences are the out-of-band fingerprint compare and the audit trail.
- **F3-L2 Bounded by G-L5.** A compromised server that gets a registry version accepted with a new admin key (ADR 0011 G-L1 and G-L5 part 1) can sign a binding with that key. F3 closes the path where the server merely reports an operator, not that one.
- **F3-L3 Same-user code.** F3 is no boundary against same-user code (ADR 0012). It can delete or edit the binding file: deleting gives `operator_binding_pending` when the switch is on, and an edit fails verification. It can also replace the pinned root or return the workspace to standalone (M2 limit 4).
- **F3-L4 Connectors older than this build.** They ignore the switch. `sandbox status` on a new connector shows the binding state; the server cannot prove what an old one enforces.
- **F3-L5 Before the switch reaches a device.** A device that has not yet applied a bundle with the switch on stays on the server-reported operator, and a compromised server can keep it there by withholding that bundle (M2 limit: a compromised server can withhold policy). `sandbox status` shows the switch and binding state on the laptop, and the page cannot be trusted for this. Setting the switch in a pilot's first bundle closes the gap for a device whose first bundle is that one.

### Consequences

- **Tests first (T9b, qa).** A forged, wrong-device, wrong-org, browser-signed, device-signed and non-admin binding are each refused. With the switch on, an unbound device refuses every remote approval and still applies a deny. With the switch off, M2 behaviour is unchanged and `m2_gate.py` stays 88/0/0. A hand edit of `enrollment.json` changes nothing once bound. A switch from true to false with one approval is refused, and so is a bundle that drops the field with one approval. A managed device with no operator refuses every remote approval. After T9b the T4 property test is rerun over bundles that set and drop the switch.
- **TCB.** `domains.py`, `protocol/registry.py`, `sync/bundles.py` (`_loosened_approval`, `_meet_approval`), `sync/verified_state.py`, `sync/enroll.py`, `approval.py`, `cli/sync_cmds.py`, all through T9b with security (L) by node id. S1's "no edit" binds T4's import, not this later change; the server inherits the new rule by importing it.
- **Frozen list.** Founder ruling T0b-2 (5 Nov 2026) approved the row: M3_PLAN frozen item 4 now allows the new tag `agg/device-binding/v1` and the new bundle field `approval.require_operator_binding`, both for T9b. No signed field set named in that item changes.
- **Terminal step.** Success metric 4 and gate item 9 say the founder never opens a terminal on the admin side. The binding step is one, because of item 2. Founder ruling T0b-1 (5 Nov 2026) gives both lines a named carve-out for this one admin CLI step per laptop.
- **Security properties.** None loosened. The switch only adds refusals when on, and turning it off takes two signers. A default of false leaves exactly today's named limit in place until a device applies the switch (F3-L5); it opens no new downgrade.
