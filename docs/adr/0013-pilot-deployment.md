## Next action

## Context

1. M2's trial needed a hosts-file hack, `--ca` and a 25-minute script. A pilot cannot start that way.
2. The pitch is that agent logs stay inside the buyer's network. The same choice keeps the audit data and the bundle-signer key there.
3. Today's `ee/deploy/compose.yml` is a demo: Caddy `tls internal`, ports on 127.0.0.1, Keycloak with `admin/admin` and a tmpfs H2 database, and the `caddy-root-cert` and `ca-bundle` steps. The `api` process has no notion of a deployment profile.

## Options

1. **Compose on the partner's Linux VM, one script (chosen, ruling 1).** No per-tenant cost to us. A partner needs one VM of 2 vCPU and 4 GB (about 20-40 USD a month, an estimate) and a DNS name they own.
2. **Hosted single tenant.** It puts us in the compromised-server seat with their audit data and bundle-signer key, and needs backups, on-call and a security story we cannot yet make, at about 40-80 USD per tenant per month (an estimate) against a 100 USD credit. Rejected as a product. Hosted or multi-tenant is an M4+ question once a paying pilot asks (ruling 1).
3. **Helm.** ADR 0005 stands: later.
4. **IdP, PM against lead.** PM: bundled Keycloak only. Lead: Keycloak by default plus a documented switch. Founder: lead's option (ruling 1).

## Decision

1. **One script.** `ee/deploy/pilot.sh up|doctor|backup|restore|upgrade` on a Linux VM. `up` asks for the public DNS name and IdP settings, runs init-secrets, builds the web bundle in a container (`npm ci --ignore-scripts` from the lockfile), migrates with the org bootstrap, starts Caddy with ACME for that name and prints the setup code once. The code also stays in the `migrate` container log (S8; ADR 0005 M1 amendment 3), and so does the genesis code (ADR 0011). `pilot.sh` refuses the demo profile.
2. **Pilot profile asserts (rows 43, 51; `ee/tests/test_m3_t5_pilot.py` over the merged compose config).** No demo service; no `admin/admin`; no `tls internal`; no `AGG_ALLOW_DIRECT_PUBLISH`; `caddy-root-cert` and `ca-bundle` gone; `SSL_CERT_FILE` unset, so the api uses its TLS library's default public roots (httpx uses certifi, measured on 0.27.2); `AGG_OIDC_ALLOW_HOSTS` set to the IdP host; `caddy-data` mounted by `proxy` only (S4); Keycloak admin paths unrouted; secrets 0400. Lead: the api gets `AGG_DEPLOY_PROFILE=pilot` from the merged config and refuses to start if the direct-publish flag is present (ADR 0001 Amendment A9 item 10). Security ruling: `oidc_client_secret` stays 0440, owner 65534, group 30000, as the one named exception on the bundled Keycloak path. The test asserts exactly that file and mode, and that only `api` and `keycloak` carry group 30000. No file split: both services must hold the same value at runtime, so two 0400 copies move no boundary and add a way to drift on rotation. With the partner-IdP switch set, no Keycloak runs, so the file is 0400 for uid 10001 and no service carries the group. Every other secret, the new pilot secrets included, is 0400.
3. **TLS.** Caddy with ACME for the public name; this replaces customer cert files as the pilot default (ADR 0005 2.1, amended). HSTS stays on. Connectors verify through the OS trust store. Lead: `up` checks that the name resolves to this VM and that ports 80 and 443 answer from outside, and stops with a named refusal if not. There is never a fallback to `tls internal`. Security: Caddy itself serves a name from its local CA when the name cannot get a public certificate (`localhost`, an IP address, `.local`, `.internal`, `.home.arpa`), with no `tls internal` line anywhere. So `up` refuses those names and private addresses, the pilot config names its ACME issuers explicitly, and the T5 test asserts on the adapted config that no internal issuer appears. If no certificate arrives within a stated time, `up` stops with that named refusal; a retry between public CAs is fine. Issuance and renewal need the VM reachable from the internet on those ports, and `PILOT.md` says so.
4. **Identity provider.** **Default: a bundled Keycloak pilot realm.** The admin password comes from a secret file through `KC_BOOTSTRAP_ADMIN_PASSWORD`, exported in the entrypoint as the client secret is today. `/admin/*` and `/realms/master/*` are not routed on the public name, so the admin console is reached by SSH tunnel only. Brute-force protection on, self-registration off. Its own Postgres role and database, with no grant on `agg` (S8, row 51). **Switch: the partner's own OIDC provider,** a config setting with ten lines of documentation each for Entra ID, Okta and Google Workspace, tested once on an Entra free developer tenant in T5. With the switch set, no Keycloak service runs. No bespoke IdP work (PM cut 4).
5. **`doctor`.** Prints a scrubbed bundle. It redacts `postgresql+psycopg://user:pass@` URLs, the setup code, everything under `secrets/`, every token and any PEM `PRIVATE KEY` block wherever it appears. A test plants a fake secret and asserts it is absent (S8, row 52).
6. **`upgrade`.** Only to a verified signed release tag. It verifies the tag's signature before it unpacks anything, backs up, migrates, and refuses a migration downgrade (S8, row 50). Lead: S8 allows "signature or printed archive sha256" and D4 says sha256; this ADR takes the signature, because a sha256 fetched from the same place as the archive proves nothing. The verifying public key is pinned in the installed `pilot.sh`, and `PILOT.md` prints its fingerprint so the first download can be checked by hand. A validly signed older tag is refused too: the target version must be above the installed one. The repository has no tags today and no release signing key is recorded, so the founder creates one and holds it offline before T10 (ruling T0b-5).
7. **`backup` (S4 MUST 1, row 44).** One encrypted archive of `pg-data` and all of `secrets/`, optionally with `caddy-data` (the TLS key and ACME account key), which appears only inside this archive. Reason: the bundle-signer key is listed in every pinned registry, so losing it blocks every new bundle until an admin-quorum rotation, and the pg role passwords and OIDC client secret must match `pg-data`. Encryption is age. The VM holds only the public recipient; the private key is held by the partner and never sits on the VM. `backup` refuses to write plaintext and streams straight into age, so no plaintext copy lands on disk. Lead: the database is quiesced for the copy so the archive is not torn; T10 records the outage in seconds. Security: the api comes back up on every exit path, and laptops keep enforcing during the outage. `backup` prints the archive's sha256 for the partner to record off the VM.
8. **`restore` (S4 MUST 2).** Drilled in T10 by `m3_pilot.py --restore-check`. Registry head, maximum sequence per project, record counts and `audit verify` must be equal before and after, and one enrolled device's next `sandbox sync --once` must report no `server_head_mismatch`. Lead: the archive is decrypted off the VM and streamed in over SSH, so the key rule holds during a restore too. Security: age does not say who wrote an archive, and the recipient key is public, so `restore` takes the recorded sha256 as a required argument and the operator checks it before decrypting. A restored database is checked against the expected root fingerprint before the api starts. `restore` writes no temporary plaintext and adds an `admin_audit` row naming the archive hash after the data is back, since the restored chain cannot show the event by itself.
9. **Hosted only for our demos.** One hosted single tenant on the Azure credit, for our own discovery-call demos, running this same script, so the install path is proven each time we demo. No partner data on it.

## Partner-supplied certificate path

Founder ruling T0b-3 (5 Nov 2026, `M3_PLAN.md`): ACME is the first path built, internet-facing on 80 and 443. This second path is for a VM with no inbound internet. It lands inside T10, after T5, and T5's 5 days are unchanged (date slices dropped by ruling T0b-10). Lead and security recommended ACME only; this path is the founder's call. Security (L) confirmed the design as edited here on 5 Nov 2026 (`docs/control-plane/T0B_SECURITY_REVIEW.md`, addendum) and reviews T10's diff. No VM, Caddy or partner CA has been run. The only measurement is the connector and httpx trust check named in items 6 and 8: one run on loopback with a throwaway CA, on the Windows laptop, venv Python 3.12.10.

1. **Switch.** `pilot.sh up --tls-cert <fullchain.pem> --tls-key <key.pem> --tls-ca <ca.pem>`. All three or none; a partial set is a named refusal. With none on a first install, the ACME path in item 3 of the Decision is unchanged. `up` never moves between the two paths by itself: the stack records its path in a non-secret file, a later `up` or `upgrade` with no flags keeps the recorded path and its files, and asking for the other path is a named refusal in M3.
2. **No fallback.** Each site block is `tls <cert> <key>` from the supplied files, and that covers every listener, including the `:443` address the api reaches on the `idp` network. The global option `auto_https disable_certs` is set, so a name the certificate does not cover gets no certificate rather than one from a local CA. The merged config holds no `tls internal`, no `local_certs`, no `auto_https ignore_loaded_certs` and no ACME issuer, and the base `proxy` entrypoint that waits for a local root does not carry over. If the files do not load, Caddy does not start and `up` stops with a named refusal; it does not retry with ACME or a local CA. Every site name is still checked in item 3, the IdP's name included if open question 2 gives it its own, and the T10 test asserts on the adapted config rather than relying on Caddy's docs.
3. **Names (lead's design call, confirmed with additions).** Names are compared lower-case, in A-label form, with no trailing dot.
   - **Refused even with a covering certificate:** `localhost`, `*.localhost`, every IP literal, including any name whose last label is numeric, and any single-label name. `localhost` resolves to each laptop itself, a single label depends on each laptop's search domain, and the pilot needs one DNS identity for its OIDC redirects.
   - **Accepted only when the certificate covers them:** `.internal`, `.local` and `.home.arpa`. Covered means a `subjectAltName` dNSName that matches exactly, or a wildcard in the left-most label only, matching one label, with at least two labels after it (`*.internal` covers nothing). A common name alone does not count. With no covering certificate these stay refused.
   - **Private addresses:** a name may resolve to a private address on this path. The refusal in item 3 of the Decision stays in force on the ACME path.
   - **Reachability check.** Item 3's check from outside does not apply. `up` checks that the name resolves on the VM, then makes a TLS connection to the name on 443, verified against `ca.pem`, and compares the leaf's fingerprint with the supplied one. It cannot check a laptop's path to the VM; a laptop's first `sandbox enroll` is that check.
4. **Refused before Caddy starts, each by name.** A key that does not match the leaf. A passphrase-protected key, since nothing may hold the passphrase on disk. A leaf that is expired or not yet valid. A chain that does not verify to `ca.pem` with no partial-chain mode, so `ca.pem` holds roots. A certificate in `ca.pem` without `CA:TRUE`. A leaf with `CA:TRUE`. A leaf whose extended key usage omits `serverAuth`. A `PRIVATE KEY` block in `fullchain.pem` or `ca.pem`. A source key that is a symlink or is readable by group or others. Two cases are accepted with a printed warning: a wildcard leaf, because its key on this VM also speaks for the partner's other hosts, and a leaf valid for more than 398 days, because nothing checks revocation (limit below). The partner's CA key never comes to the VM.
5. **Files, modes, who reads.** `secrets/tls_partner_key`: 0400, owner 65532:65532, the uid `proxy` runs as. `_write_secret` in `init-secrets.sh` creates with `O_EXCL` and prints `SKIP` when the file exists, so it cannot rotate. A new helper in that script does both install and rotation: it reads the key on stdin, never argv or env, writes a temp file in `secrets/` at 0400, sets the owner, syncs and renames over. It is a compose secret mounted by `proxy` only, and read only by the Caddy process. `api`, `keycloak`, `migrate` and the one-shots never mount it. `up` says that the source file is a second copy of the key and that the partner should remove it. `pilot-tls/fullchain.pem` and `pilot-tls/ca.pem`: 0444, owner root, public, git-ignored, outside `secrets/`, so `doctor`'s rule that everything under `secrets/` is redacted holds without an exception. `caddy-data` stays mounted by `proxy` only (S4). It holds no TLS private key on this path, so `backup` leaves it out by default. `backup` carries `secrets/` as before, so the key is in the archive, and adds `pilot-tls/` on this path, inside the same one encrypted archive. `restore` puts back owner and mode and reruns the item 4 checks before `proxy` starts, so an old archive with an expired or replaced certificate stops at a named refusal. Root on the VM can read the key (named limit "One machine").
6. **Trust inside the stack (security ruling, narrower than the first draft).** The api's only outbound TLS is OIDC discovery, JWKS and token calls, through one `httpx.Client` built at startup (`ee/src/agg_cp/app.py:64`). httpx takes `SSL_CERT_FILE` as a replacement for its bundle, not an addition (measured on 0.27.2: 121 roots unset, 1 with the file set; `ee/pyproject.toml` allows later versions, so T10 asserts this on the image). So the api gets only what it needs:
   - **The IdP chains to `ca.pem` (a bundled Keycloak, or a partner IdP the operator declares as internal).** `SSL_CERT_FILE=/pilot-tls/ca.pem`, one read-only file mount on `api`. This is the one exception on this path to item 2 of the Decision, whose wording follows S4's "with ACME". There is no one-shot and no system CA in it. `caddy-root-cert` and the base `ca-bundle` stay gone, and nothing reads `caddy-data`.
   - **A partner IdP on a public CA.** `SSL_CERT_FILE` stays unset and item 2 of the Decision holds as written, so the partner's CA never speaks for that IdP to the api.
   - **Checks.** `up` makes one verified connection to the issuer from the api image with the chosen trust and stops with a named refusal if it fails; it never widens trust to make it pass. `AGG_OIDC_ALLOW_HOSTS` stays exactly the IdP host; that entry also skips the private-address check for that host (`ee/src/agg_cp/oidc.py:402`), so nothing else goes in it. The https rule (`oidc.py:390`) and the exact issuer match (`oidc.py:448`) still apply to it. For a bundled Keycloak, the `idp` network alias on `proxy` is the real IdP name, as `idp.localhost` is in the base file. The `proxy` health check verifies against `ca.pem` using the real name; the base file's `curl -sfk` does not carry over.
7. **Expiry is the partner's job.** Nothing renews these files and nothing contacts the partner's CA. `doctor` reports the leaf's `notAfter`, days left, SANs, SHA-256 fingerprint and whether the chain verifies to `ca.pem`. It warns at 30 days or fewer, and when expired it says `EXPIRED` and exits non-zero. It reads only the public files. Rotation is `pilot.sh up` with the new files: the item 4 checks run on the new pair before anything is replaced, and `proxy` is recreated, with a short outage since the Caddy admin endpoint is off. If `ca.pem` changed, `api` is recreated too, because its client loads trust at startup, and `up` prints the new SHA-256 because every laptop using `SSL_CERT_FILE` needs the new file. After expiry, browsers and laptops refuse the connection. HSTS leaves no click-through. Sync and enrolment stop, laptops keep enforcing locally, and the server shows `device_silent`.
8. **How the laptop connector trusts it. Verification is never disabled.** The connector builds no TLS context: `sandbox enroll`, `sandbox sync` and `sandbox signer` use `urllib` with Python's default context, which checks the chain and the hostname (`src/sandbox/connector/sync/enroll.py:119`, `src/sandbox/connector/sync/process.py:160-175`, `src/sandbox/cli/sync_cmds.py:957`). `http://` to a non-loopback host and redirects are refused before any token leaves (`process.py:112-125`, `:154-158`; `sync_cmds.py:907-947`). So this path needs no connector diff and touches no TCB file. Measured through `_default_connect` and plain `urlopen`: an unknown CA is refused, a name mismatch under a trusted CA is refused, and `SSL_CERT_FILE` naming the CA is accepted.
   - **OS store.** On Windows, Python's default context loads the Windows `ROOT` and `CA` stores (read in `ssl.py`; not yet run with a partner CA in the store, a T10 exit item). A Windows laptop whose IT has deployed the internal CA needs no step.
   - **`SSL_CERT_FILE`, the documented alternative where the CA is not in that store.** ADR 0001 A6 item 2 already says the OS trust store or `SSL_CERT_FILE` applies, and QUICKSTART uses it. It points at a local copy of `ca.pem`, kept outside any workspace root. On Windows it adds to the OS stores (measured: 266 certificates to 267). On POSIX, OpenSSL's default file is replaced, so the file must hold what the process needs. macOS is expected to need this because Python's OpenSSL does not read the Keychain, to be confirmed in T10. Set it for the `sandbox` commands, not the whole shell profile; a background `sandbox sync` needs it in its own environment.
   - **Where `ca.pem` comes from.** From the partner's IT, out of band, never fetched from the VM over an unverified connection. `up` prints its SHA-256, and the admin hands that over with the root fingerprint.
   - **The anchor does not move (confirmed against code).** An operator-chosen CA vouches for a name, not for the server's authority. `enroll` computes the fingerprint from the genesis it received, compares it with the mandatory `--expect-fingerprint`, runs `verify_chain`, and writes nothing on a mismatch (`enroll.py:83-84`, `:134-150`). Every later registry and bundle verifies against the pinned root. A bad server with a valid certificate fails there unless the admin hands over its fingerprint, so the fingerprint must travel out of band, never from a page read through the same path.
   - **`--ca-pin` (C-L1) stays a D5 SHOULD and is not a MUST for this path (security ruling).** Private-CA trust works without it, as measured. Its purpose is to stop another certificate impersonating the server, a risk both paths share. Impersonation gives transport access (limit below), not a way past the pinned root. If it lands, it only adds a refusal, and `PILOT.md` names it as the stricter option. No flag that skips verification is added, and `PILOT.md` must never suggest `PYTHONHTTPSVERIFY=0`, an unverified context or `curl -k`.
   - **Browsers** use the OS or browser store, which is the partner's IT's job.
9. **Ports.** This path publishes 443 only, on the interface the partner names. The base file's two `127.0.0.1` entries are replaced, not merged, and the test asserts the merged result. HSTS stays on, with `includeSubDomains`, for two years, so `PILOT.md` says to use a dedicated host name, never a name whose subdomains the partner serves over plain HTTP.

### Named limits on this path

- **Inbound only.** It removes the need for inbound internet. Outbound access at install and upgrade (images, `npm ci`) is still needed; an air-gapped install is not designed.
- **Who holds the CA.** Anyone holding the partner's CA key, or a TLS inspection proxy the client trusts, is the compromised-server case of the M2 limits for whoever connects through them. They can read bearer tokens, enrollment codes and session cookies on the wire. They can also serve the page's JS, so ADR 0003 M2 amendment 7.2 applies: non-prod remote approvals and denies can be signed with the browser key of any user who loads the page, dual approvals by two browser keys included. They cannot sign what needs a CLI key (registries, loosening, un-enrol), approve on prod, or change a laptop's pinned root. `PILOT.md` tells the partner to exclude this name from TLS inspection and, where they cannot promise that, to approve with CLI keys. Unlike ACME, no public log shows a certificate issued for this name.
- **No revocation check.** Neither the connector nor httpx checks CRL or OCSP (measured: 0 CRLs loaded). A stolen partner key stays useful to someone on the network path until the leaf's `notAfter`, even after rotation, unless clients stop trusting the CA.
- **The key's reach.** The key sits on the VM and in every backup archive. With a wildcard leaf, that reach covers the partner's other hosts.
- **Laptops need a network path to the VM.** That is the partner's VPN or LAN; T10 uses a tunnel and exercises no partner VPN.
- **Wording.** "No inbound internet needed" applies to this path only and only after T10's exit. F-5's bar on "nothing leaves your network" still holds on both paths.

## Named limits (for `docs/PILOT.md`; exact wording settled at T14)

- **Three named people for the first bundle (ruling T0b-6).** A proposer and two approvers, with approver keys from a registry version with two admin signatures.
- **A device behind a registry change (F-1, ruling T0b-8).** Named here until the T9b fix lands. See the consequence in ADR 0001 Amendment A9.

- **IdP fixed at org creation.** `sub` is the registry user id. Moving realms later, for example from the pilot realm to Entra, orphans every key. A partner starts on the IdP it keeps (S8).
- **Restoring an older state.** It raises `server_head_mismatch` on every device, by design (S4). A device already past the restored sequence keeps its last bundle and is served nothing until the server's sequence passes its own, and a device enrolled after the backup has no server row and loses its token. Recovering such a device early takes an admin-quorum un-enroll and a new enrolment, because `sandbox enroll` refuses while the same root is pinned. The restore also rewinds the server: device revocations, role changes and key-link state made after the backup are undone and must be redone by hand, consumed enrolment codes and sessions from before it may be live again, and audit rows uploaded since the backup are gone from the server. `PILOT.md` lists these steps, and security's reading is that a restore to an older state is an incident, not routine.
- **One machine.** The database, the bundle-signer key and, on the default path, the IdP share one VM. A VM compromise is the compromised-server case of the M2 limits. No HA Postgres (M5).
- **Not measured yet.** "Under 60 minutes" is a target until T13 records a name and times. VM sizing and cost are estimates until T5.

## Consequences

## Security properties affected

1. **Audit data and bundle-signer key:** stay inside the partner's network; none on our side.
2. **Secrets off the VM:** only in one encrypted archive, with the key never on the VM.
3. **Attack surface:** public ports grow from loopback to 80 and 443 on the ACME path, or to 443 on the partner's network on the partner-certificate path; the Keycloak admin surface stays unrouted; demo credentials and the direct-publish path cannot start under this profile.
4. **Supply chain:** a signed tag on upgrade; `npm ci --ignore-scripts` from the lockfile.

No guarded property is weakened.
