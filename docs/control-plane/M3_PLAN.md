## Goal

1. A partner's security lead, with one browser and one laptop, can: log in with an identity provider; issue an enrollment code to a developer; see devices, bundle proposals and history, escalations with full context, and alerts; approve an action with a second named person; and download an evidence pack that verifies offline. No route call, no `psql`, no script of ours.
2. The control plane's own record of policy is truthful: a bundle is stored as approved policy only after the server verifies its change approvals with the connector's own code (named limit 7.1 closed; ADR 0001 Amendment A1 item 6).
3. One deployment story a partner can run in under an hour from a written page, with TLS and an identity provider.
4. The M2 security follow-ups land with owners and tags, and every M2 guarded property holds (local enforcement authoritative and fail-closed; models only add scrutiny; every privileged decision signed and chained; dual control is two distinct registry humans; hand edits cannot loosen).

**What we sell in M3 (market check, 4 Nov):** the approval moment. Two named humans, each signing the exact bytes that will run, verified on the laptop against a pinned registry, with offline-verifiable evidence (AIUC-1 D003.4 made human-approval workflows a core control on 15 Oct). Blocking on the laptop (Runlayer Enforce, native permission rules) and central policy push (Claude apps gateway, Codex config-server) are no longer billable on their own; ours differ only because a loosening needs two signers and the laptop verifies them.

**The M3 statement.** M3 turns the control plane into something a security lead can run as a two-week pilot without us on the call. The free security layer (MIT) blocks dangerous coding-agent actions on the developer's machine; the paid, self-hosted, cross-vendor control plane adds what a security team needs to roll it out: named people approving from a browser with keys bound to their identity, two different humans for every loosening, a central tamper-evident audit, and evidence that verifies offline. In M2 every piece was proven on one Windows laptop (88 of 88 gate checks, 4 Nov 2026) but driving it needed raw API calls and the founder's own scripts. M3 ships the web app and the one-command deployment so a partner's own admin enrols a device, publishes a policy with two approvals, sees the first escalation, approves it with a colleague, and downloads the evidence, with no terminal on the admin side and no call to us. Success is measured, not claimed.

## Design decisions and ADRs needed (T0b, before code; security confirms in writing; S1-S4 are the cited rulings)

### D1. Web app (frontend-engineer; design note in `ee/web/README.md`)
1. One React app with `react-router` (new dependency; Tailwind stays; no UI kit). Pages in build order: Approve (inbox list plus `/approve/{id}` with full context), Devices and enrollment (codes issue and status, device list and detail with quarantine badge, revoke), Policy (proposals, publish, history), Alerts (with ack), Evidence (download, verify result, JSONL export), Settings (org users and roles, already served). Strict CSP unchanged; no inline scripts.
2. The M2 signing code (`inbox.ts` payload builder, `signing.ts`, `browser-key.ts`, `key-store.ts`) is byte-identical in M3. The approve page adds context around it and the exact server refusal reason (`same_user`, `requester`, `wrong_kind`, `prod_refused`, `clock_skew`, `awaiting_second`).
3. **Rendering (S6, row 49).** Every device- or server-supplied string renders as text with the ADR 0010 rule 7 escaping; a grep test refuses `dangerouslySetInnerHTML` and `innerHTML`. Never rendered or stored client-side: the enrollment code outside the operator's one-time page (not in a URL, `history.state`, localStorage or IndexedDB; `Cache-Control: no-store`), `code_hash`, session or CSRF tokens in URLs or DOM attributes, OIDC tokens, command output (the server never receives `stdout`/`stderr`; `upload_escalation` strips or refuses the keys, with a test). Publish, revoke, stop and code issue need a session younger than 15 min or re-auth.
4. Every destructive action is a confirm step showing the object's id and hash, audited in `admin_audit`. The page is never a trust anchor: the diff a signer acts on is the one `sandbox signer` computes from the bytes on their machine; the page shows the proposal hash for comparison.
5. **Testable exit (Q1).** `ee/web/tests/m3_t2_routes.test.ts` (vitest, `@testing-library/react`, `jsdom`) renders the router against the frozen `ee/web/tests/fixtures/m3_routes.json` (path, title, action buttons per page) and fails on any missing route or button; runs in `ee-web`. The e2e proof is T6 in a real browser.

### D2. Bundle publish with server verification (ADR 0001 Amendment A4)
1. **Proposal, approvals, publish.** An admin pastes the policy JSON on the Policy page (or `sandbox signer propose-bundle`); the server canonicalises, refuses unknown fields, computes the hash and the per-section diff against the currently served bundle from the bytes, and stores a proposal. Approvers run `sandbox signer approve-change <id>`, which fetches the canonical bytes, shows its own diff and signs `agg/policy-change/v1` over the bundle hash with a CLI key; the page shows approvals by person and kind. Publish is a server step from the page or `sandbox signer publish <id>`. The admin side needs no terminal; approvers do.
2. **Verification = the connector's code, import-only (S1).** The server imports `loosened`, `_bundle_hash`, `_verify_envelope_structure`, `_verify_change_approvals` and `BUNDLE_FIELDS` from `src/sandbox/connector/sync/bundles.py` by name, with no edit and no alias (an alias is a TCB diff); `verify_and_apply` itself never runs on the server. The registry is a `Registry` from `sandbox.protocol.registry.verify_chain` over the server's own stored chain (`sync/registry.py::get_chain`), never the request body and never the `approver_keys` projection. Base: loosening against the last `server`-verified row, else deny-all; `base_sequence` must equal the max stored sequence of any label, so an M2 stack's first bundle after upgrade needs two approvals (`PILOT.md` says so). Roles: the connector's set. A stale base is refused at approval and at publish. Failure is 400 with the reason and nothing written. The connector stays authoritative on the laptop.
3. **Migration.** `policy_bundles` gains `verified_at` and `verification` (`server` or `m2_unverified`); existing rows and any direct publish are `m2_unverified` and the page labels them. Server logic reads `server` rows only. **The unconditional server-side refusal of operator self-approval stays (S2):** operator binding is TOFU until F3, so honouring `allow_requester` centrally would recreate the F-8 shape; revisit only after T4 and F3, by founder decision.
4. **Direct publish (Q3).** `POST /admin/bundles` returns 410 unless `AGG_ALLOW_DIRECT_PUBLISH=1`, which the api honours only with the demo profile and which makes the api refuse to start under the pilot profile; shipped in the T4 commit so the byte-frozen `m2_gate.py` and `demo.py` keep passing. Tests: `test_direct_publish_410_without_flag`, `test_direct_publish_rows_labelled_m2_unverified`, and `test_m3_t5_pilot.py` asserts the pilot compose never sets it.

### D3. Enrollment-code admin flow (ADR 0001 A1.1 unchanged)
Admin page: pick project and operator, issue; the code is shown only to the operator, on their own page, in a fresh session, once (`test_code_second_read_404_and_no_store_header`), with the `sandbox enroll` line and the fingerprint labelled "confirm out of band" (the CLI still refuses without `--expect-fingerprint`). CLI parity: `sandbox signer issue-code`. **CSRF (S5, row 48):** T3 adds the `X-CSRF-Token` check to `POST /admin/enrollment-codes` (`ee/src/agg_cp/sync/enroll.py:301-346`) and `POST /admin/devices/revoke` (410-445) and a catalog test over `x-agg-rbac` that every session or admin POST and DELETE refuses 403 without the header. If F3 moves to M4, the device page labels the operator "server-reported".

### D4. Pilot deployment (ADR 0013)
1. **Compose on the partner's Linux VM, one script.** `ee/deploy/pilot.sh up` asks for the public DNS name and IdP settings, runs init-secrets, builds the web bundle in a container (`npm ci --ignore-scripts` from the lockfile), migrates with the org bootstrap, starts Caddy with ACME for that name, prints the setup code once. Under the pilot profile the `caddy-root-cert` and `ca-bundle` steps are gone (system CAs; `SSL_CERT_FILE` unset) and `AGG_OIDC_ALLOW_HOSTS` is the IdP host. `doctor` prints a scrubbed bundle (redacts `postgresql+psycopg://user:pass@` URLs, the setup code, everything under `secrets/`, every token; a test plants a fake secret and asserts absence). `backup` writes one encrypted archive (age; key held by the partner, never on the VM; refuses plaintext) of `pg-data` and all of `secrets/` (the bundle-signer key is in every pinned registry; losing it blocks every new bundle until an admin-quorum rotation) and optionally `caddy-data`; `restore` is drilled in T10. `upgrade` only to a release tag whose archive sha256 `pilot.sh` verifies, backs up before migrate, refuses a downgrade. The demo profile is refused and a test asserts no demo service, no `admin/admin`, no internal TLS.
2. **Identity provider.** Default: a bundled Keycloak pilot realm (admin password from a secret file via `KC_BOOTSTRAP_ADMIN_PASSWORD` in the entrypoint; `/admin/*` and `/realms/master/*` not routed on the public name, SSH tunnel only; brute-force protection on, self-registration off; its own Postgres role and database with no grant on `agg`). The partner's own OIDC provider is a config switch, documented for Entra ID, Okta and Google Workspace in ten lines each, tested once on an Entra free developer tenant in T5. **Named limit for `PILOT.md`:** the IdP is fixed at org creation because `sub` is the registry user id; moving realms later orphans every key, so a partner starts on the IdP it keeps. No bespoke IdP work (PM cut 4).
3. **Why not hosted single tenant.** The pitch is that agent logs stay inside the buyer's network. Hosting puts us in the "compromised server" seat with their audit data and bundle-signer key, needs backups, on-call and a security story we cannot yet make, at 40-80 USD per tenant per month against a 100 USD credit. One hosted single tenant on the Azure credit serves our own discovery-call demos only, running the same script. Partner cost: one 2 vCPU, 4 GB VM at 20-40 USD per month and a DNS name they own.

### D6. Device-level quarantine and the signed stop (ADR 0014; option T11, sized not committed)
`agg/stop/v1` (org, project, device or all, reason, issuer user id and key id, nonce, `not_after` at most 24 h after issue) is tighten-only, so one active registry key signs it: new tag in `domains.py` and a `may_sign` row in `protocol/registry.py` for kinds `cli` and `browser` with role `approver` or `admin`; device and bundle-signer keys refused; allowed on prod; nonce per `(key_id, nonce)`; fresh-session rule in the browser; the connector verifies against its pinned registry only (S3). Triggers: a verified stop, or the connector's own `audit_fork` detection (a server `audit_quarantine` row alone never changes connector state). Effect: every call denied except reads inside the root; `sandbox status`, the device badge and the alert show it; entry and release are chained records naming the stop hash or fork record. Release is only a two-CLI-user loosening bundle naming the stop id. Limits stated in the product: takes effect at the next hook call or poll; running children are not killed; a laptop that never syncs is caught by `device_silent` only. Wording: "a stop button and the proof of what the agent did"; never "kill switch" or "EDR".

M3 delivers the ADR plus a measured spike on the Windows laptop (a second local account holding the device key; what breaks in `FolderBroker.execute`), not a build.
