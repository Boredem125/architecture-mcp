# Self-hosted control-plane deployment

## Prerequisites

- Docker Engine 24+ and Docker Compose v2
- Node.js 20+ and npm (for the web bundle build)
- (Optional) Trivy CLI for image scanning
- (Optional) ZAP CLI or Docker image for baseline scan

## Quick start

### 1. Generate secrets (first time only)

```bash
cd ee/deploy
docker compose --profile init run --rm init-secrets
```

This creates random credentials and pre-composed database URLs in
`./secrets/`.  Each file is chowned to the uid:gid of its consumer
service with mode 0400 (single consumer) or 0440 (shared via group).
To regenerate, delete all files in `secrets/` except `.gitignore`
and re-run the command.

### 2. Build the web bundle

```bash
cd ../web && npm ci && npm run build
cd ../deploy
```

### 3. Start the stack

```bash
docker compose up -d --build
```

Services: `postgres` (internal only), `migrate` (one-shot), `ca-bundle`
(one-shot), `api`, `proxy` (Caddy, ports 443/80 on 127.0.0.1).

### 4. Read the setup code

```bash
docker compose logs migrate
```

Look for the JSON line:

```json
{"event":"setup_code","org":"<slug>","code":"<code>","expires_at":"..."}
```

Use this code on first login to become the org admin.  The code expires
after 30 minutes and is single-use.

### 5. Verify readiness

```bash
curl -sk https://localhost/ready
```

Expected: `{"status":"ok"}` (HTTP 200) once the API is up and the DB
schema is at the Alembic head.

### 6. Security scans

```bash
# Trivy -- container image
docker compose build api
trivy image $(docker compose images api -q) --severity HIGH,CRITICAL

# Trivy -- filesystem
trivy fs .

# ZAP -- baseline scan against the proxy
docker run --rm --network host \
  ghcr.io/zaproxy/zaproxy:stable zap-baseline.py \
  -t https://localhost -I
```

## Demo profile (Keycloak)

The demo profile adds a Keycloak instance with two demo realms (Acme,
Globex) and three users, plus an IdP reverse-proxy site on Caddy.

### Start the demo stack

```bash
AGG_OIDC_ALLOW_HOSTS=idp.localhost docker compose --profile demo up -d --build
```

On Windows, the host does not resolve `idp.localhost` (browsers and most
Linux resolvers map `*.localhost` to loopback; Windows does not). Before
running `demo.py` or logging in from a non-browser client, add this line to
`C:\Windows\System32\drivers\etc\hosts` as administrator:

```
127.0.0.1 idp.localhost
```

`demo.py` verifies TLS against Caddy's local root CA. On Windows the
`/ca-bundle` path does not exist, so copy the CA out and pass it:

```bash
docker compose cp proxy:/data/caddy/pki/authorities/local/root.crt ./caddy-root.crt
python ee/deploy/demo.py --ca ee/deploy/caddy-root.crt
```

Delete `caddy-root.crt` afterwards; it is not a secret, but it is local state.

The demo profile starts everything from the base stack plus:
- `keycloak` -- Keycloak 26 with imported demo realms
- `migrate-demo` -- bootstraps the `acme` org (OIDC config + setup code)

The `idp.localhost` site is served by Caddy with `tls internal`.  The
API trusts this certificate via a combined CA bundle (the `ca-bundle`
one-shot service merges the system CAs with Caddy's internal root CA).

### Read the setup code

```bash
docker compose logs migrate-demo | grep setup_code
```

### Demo users

| User  | Realm  | Password              |
|-------|--------|-----------------------|
| alice | acme   | `demo-only-alice-123` |
| bob   | acme   | `demo-only-bob-456`   |
| eve   | globex | `demo-only-eve-789`   |

Keycloak admin: `admin` / `admin` (demo only).

### OIDC client secret

The demo realm JSON uses the Keycloak env-var placeholder
`${AGG_DEMO_OIDC_CLIENT_SECRET}` for the client secret.  The Keycloak
entrypoint reads the compose secret `oidc_client_secret` (generated by
init-secrets) and exports it as `AGG_DEMO_OIDC_CLIENT_SECRET` before
Keycloak starts, so the imported realm uses the same secret as the API.
No manual sync is needed.

### Bootstrap the Globex org (second org)

The demo realm includes a `globex` realm and user (`eve`).  To
bootstrap it as a second org, run one more migrate pass:

```bash
docker compose run --rm \
  -e AGG_DATABASE_URL_FILE=/run/secrets/pg_owner_url \
  -e AGG_BOOTSTRAP_ORG_SLUG=globex \
  -e AGG_BOOTSTRAP_ORG_NAME="Globex Corporation" \
  -e AGG_BOOTSTRAP_ORG_ISSUER=https://idp.localhost/realms/globex \
  -e AGG_BOOTSTRAP_ORG_CLIENT_ID=agg-control-plane \
  migrate-demo python -m agg_cp.migrate
```

Then repeat the client-secret sync for the `globex` realm and mount
the secret file at `/oidc-secrets/globex` (add a bind mount to the
api service in `compose.yml`).

## Architecture notes

### Keycloak behind Caddy (demo)

The `proxy` container (Caddy) serves a second site block for
`idp.localhost` with `tls internal`, reverse-proxying to Keycloak on
port 8080.  Keycloak 26 uses `KC_PROXY_HEADERS=xforwarded` and
`KC_HOSTNAME=https://idp.localhost` to produce correct issuer URLs
(`https://idp.localhost/realms/acme`).

The proxy has a network alias `idp.localhost` on the internal network,
so the API resolves it to the Caddy container.  Caddy listens on port
443 (in addition to 8443) for container-to-container TLS; the proxy
has `cap_add: NET_BIND_SERVICE` to allow this.

### CA trust

The `ca-bundle` one-shot service concatenates the system CA bundle with
Caddy's internal root CA (`/data/caddy/pki/authorities/local/root.crt`)
and writes the result to the `ca-bundle` volume.  The API sets
`SSL_CERT_FILE` to this combined bundle so that httpx trusts
Caddy-issued certificates without `update-ca-certificates`.

### Secret file ownership

The `init-secrets` container (one-shot, runs as root with only
`CAP_CHOWN` and `CAP_DAC_OVERRIDE`) sets per-consumer ownership on
each secret file.  `DAC_OVERRIDE` is needed so that the container can
create files in `./secrets/` even when the directory is owned by a
non-root uid on native Linux hosts:

| Secret                 | UID:GID      | Mode  | Consumer(s)           |
|------------------------|-------------|-------|-----------------------|
| `pg_superuser_password`| 999:999     | 0400  | postgres              |
| `pg_owner_password`    | 999:999     | 0400  | postgres (00-roles.sh)|
| `pg_app_password`      | 999:999     | 0400  | postgres (00-roles.sh)|
| `pg_owner_url`         | 10001:10001 | 0400  | migrate, migrate-demo |
| `pg_app_url`           | 10001:10001 | 0400  | api                   |
| `oidc_client_secret`   | 65534:30000 | 0440  | api + keycloak (gid)  |
| `server_signing_key`   | 10001:10001 | 0400  | api                   |

Files shared between services with different UIDs use a common GID
(30000) with mode 0440.  The consuming services have `group_add: ["30000"]`
in compose.yml.  No secret file is world-readable.

Docker Compose `file:` secrets (non-Swarm) are bind mounts that
preserve host-side ownership and mode, so the chown in init-secrets
is what the container processes see at `/run/secrets/`.

### Stated limit: ca-bundle DAC_READ_SEARCH (fixed, M2 T3)

**Fixed.** The proxy entrypoint now copies only `root.crt` from
`caddy-data` to a dedicated `caddy-root-cert` named volume.  The
`ca-bundle` service reads from `caddy-root-cert` (not `caddy-data`)
and no longer needs `CAP_DAC_READ_SEARCH`.  Caddy's private keys
in the `caddy-data` volume are never exposed to `ca-bundle`.

### API base image (M2 T4)

The `api` service uses a Chainguard Python distroless base image:

- **Tag:** `cgr.dev/chainguard/python:latest`
- **Digest:** `sha256:e2ade4461c3ff67acf054214645e0b4e41b99140d7096ed64c1e15f6fe985cdf`
- **Python version:** 3.15 (the free Chainguard tier tracks latest)
- **Properties:** no shell, no package manager, non-root (uid 65532)
- **Update policy:** rebuild weekly.  Pull `cgr.dev/chainguard/python:latest`,
  record the new digest, run `docker compose build api`, then Trivy and
  the full test suite.  Pin the tested digest in `api.Dockerfile`.
- **Fallback:** if the free `:latest` tag changes Python major.minor in a
  way that breaks ABI compatibility with the wheels built in the dev stage,
  build a custom base with Wolfi via `apko` that pins the needed Python
  minor version (e.g. `python-3.15`).  The Chainguard free tier publishes
  only `:latest`, so a version pin is only available through `apko` or the
  paid Chainguard Images subscription.

### Keycloak admin password

Keycloak has no `_FILE` convention for `KEYCLOAK_ADMIN_PASSWORD`.  This
is acceptable because: internal network only, demo profile only.
